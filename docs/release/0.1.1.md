# PooledMailKit 0.1.1 Release Notes

`PooledMailKit 0.1.1` is a behavior-correction release.

A source review against the design documents found four places where the
implementation did not deliver the documented contract, plus several
robustness issues. This release fixes them without changing the public API
surface.

## Behavior Fixes

### 1. SMTP send stage is now inferred from MailKit command failures

Previously every failure during `SendAsync` was treated as `DataStarted`,
because nothing in the production code ever attached stage information. As a
result:

- `RetryableTemporaryFailure` was unreachable, so SMTP `4xx` failures were
  never retried even within the configured attempt budget.
- Every command rejection was reported as ambiguous (`UnknownAfterData`),
  inflating `pooledmailkit.send.ambiguous.count`.

The sender now derives the stage from `SmtpCommandException.ErrorCode`:

- `SenderNotAccepted` / `RecipientNotAccepted` map to `EnvelopeStarted`.
- `MessageNotAccepted` maps to `DataCompleted`.
- Other command failures keep the conservative `DataStarted` boundary.

### 2. DATA completion rejections are no longer classified as ambiguous

`MessageNotAccepted` is the server's reply to the completed `DATA` payload,
so the protocol outcome is known: the message was not accepted. It is now
classified as:

- `4xx`: `RetryableTemporaryFailure` (retryable within the attempt budget)
- `5xx`: `PermanentFailure`

In both cases the connection stays reusable, because the SMTP session
finished the transaction in a clean state. This matches the documented rule
that post-`DATA` failures are ambiguous only "unless the protocol outcome is
known".

### 3. Message-level failures no longer put the host into reconnect cooldown

Previously any discarded lease — a `5xx` recipient rejection, a caller
cancellation, or a keep-alive failure on one stale idle connection — applied
the host reconnect cooldown with exponential backoff. Under steady traffic
with occasional bad recipients this could suppress connection creation for up
to `MaxReconnectCooldown` and surface as avoidable `PoolExhausted` failures.

Reconnect cooldown is now applied only where the design documents intend it:
on connection creation failures. If a host is genuinely down, the next
creation attempt fails and the cooldown engages as before, so reconnect-storm
suppression is preserved.

### 4. Host failover now happens inside a single acquire

When connection creation failed, the pool previously threw immediately, so
multi-host failover only worked when callers enabled retries. The acquire
loop now applies the per-host cooldown and continues with the next eligible
host within the same call, matching the documented failover sequence.

When no other host is eligible and no live connection can be returned, the
acquire still fails fast with the original creation error.

`SmtpSendResult.Attempts` therefore reports `1` for sends that succeed
through in-acquire failover, because host selection retries inside acquire are
not counted as separate send attempts.

### 5. Warm-pool refill is best-effort on the send path

A `MinPoolSize` refill failure during acquire or lease return previously
propagated to the caller, failing sends that idle connections could have
served — and in the worst case reporting a server-accepted send as failed.
Refill failures on the send path are now swallowed after recording metrics;
if the underlying failure is a connection creation failure, the normal
per-host cooldown still applies. `WarmupAsync` still reports refill failures
to its caller.

### 6. A server-accepted send is always reported as success

The success path now completes the lease best-effort, so slow or broken lease
cleanup (or a cancellation that lands after the server accepted the message)
can no longer convert an accepted send into a reported failure.

## Robustness Fixes

- Removed the unused per-endpoint host dictionary in `SmtpPool`, which also
  rejected configurations that listed the same `host:port` twice.
- Retry delays now use the injected `IClock` instead of `Task.Delay`, keeping
  retry behavior deterministic under test clocks.
- Disposing the pool now wakes blocked acquires instead of leaving them to
  fail on a disposed semaphore.
- Pool state metrics snapshots are now taken under the pool lock, removing a
  benign data race on host cooldown state.
- `JitterRatio` is validated to the range `[0, 1]`; values above `1` could
  previously collapse retry delays to zero.
- Abandoned lease-cleanup tasks are observed so late faults cannot become
  unobserved task exceptions.

## Compatibility Notes

- No public API changes. `PublicAPI` baselines are unchanged.
- Failure classification output changes for two cases:
  - `4xx`/`5xx` replies to the `DATA` payload are now definitive
    (`RetryableTemporaryFailure` / `PermanentFailure`) instead of
    `UnknownAfterData`, and keep the connection.
  - Envelope rejections now report stage `EnvelopeStarted` instead of
    `DataStarted`.
- Operationally, hosts enter cooldown less often (creation failures only).
  Dashboards tracking `pooledmailkit.pool.host.cooldown.active` may show less
  cooldown activity for the same traffic.
- Multi-host deployments see failover within the first attempt; alerting that
  keyed on `Attempts >= 2` for failover should use the endpoint key instead.

- Outage stress scenarios pin `MaxReconnectCooldown` to the base cooldown so
  recovery timing stays deterministic; backoff growth remains covered by unit
  tests.

## Known Limits

- Recipient and sender rejections remain non-retryable regardless of status
  code, per the documented classification rules. Whether `4xx` envelope
  rejections (for example greylisting at `RCPT`) should become retryable is
  an open design decision.
- Keep-alive failures no longer contribute to host-level suppression at all;
  a threshold-based contribution remains a possible future extension.
