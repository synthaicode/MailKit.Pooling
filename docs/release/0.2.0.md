# PooledMailKit 0.2.0 Release Notes

`PooledMailKit 0.2.0` is an error-policy alignment release.

A source-level error-policy extraction (a full inventory of throw/catch
sites, a category-by-disposition matrix, and a contradiction list) found
four inconsistencies in how the library handles failures. This release
resolves all four. Two of the resolutions change observable behavior, so
this is a minor version bump.

## Breaking Changes

### 1. Unknown exception families are rethrown raw, not wrapped

Previously the classifier's fallback treated every unrecognized exception
type — including programming errors such as `NullReferenceException` from a
custom `ISmtpClientAdapter` — as `ConnectionCorrupted`, wrapping it in
`SmtpSendFailedException`. Bugs therefore surfaced as operational send
failures.

Now exception types outside the known SMTP failure families
(`SmtpCommandException`, `SmtpProtocolException`, transport/timeout types,
authentication types, pool exhaustion, stage-aware wrappers) are classified
as the new `SmtpFailureKind.Unclassified`. The sender still discards the
connection and records the classification metric, then rethrows the
original exception unchanged.

Migration: callers that relied on `SmtpSendFailedException` as the single
catch surface must add handling for raw exceptions. A raw exception from
`SendAsync` now indicates a bug or a foreign adapter fault, not an SMTP
outcome.

### 2. Range violations consistently throw ArgumentOutOfRangeException

All `SmtpPoolOptions` validation now lives in one internal validator used by
both `AddMailKitPooling` and direct `SmtpPool` construction. Structural
problems throw `ArgumentException`; range violations throw
`ArgumentOutOfRangeException`. Previously the DI path threw
`ArgumentException` for `JitterRatio` and host `Weight`; exact-type catches
at startup must be updated (catches of the base `ArgumentException` still
work).

## Added

### Eager configuration validation

Configuration mistakes that previously surfaced only at the first
connection attempt — presenting operationally as repeating transient
connection failures with reconnect cooldown — now fail at registration or
construction time:

- unparseable `SecureSocketOptions` names
- `Password` missing while `UserName` is set (use an explicit empty string
  for passwordless authentication)
- negative `RetryBaseDelay`
- negative `MaxRetryAttempts`

### New metric

- `pooledmailkit.pool.lease.return_ignored.count`: a lease return for an
  unknown connection id is ignored by design (lease completion is
  idempotent) and is now observable instead of silent.

## Fixed

### Edge-triggered availability signal (stale wake permits)

The pool's connection-availability signal was a counting semaphore.
Connection returns with no waiting acquirers accumulated stale permits that
could later wake a blocked acquirer immediately without a real return
event. The signal is now an edge-triggered pulse that waiters observe
before inspecting pool state: no stale state, no lost wake-ups, and the
`SemaphoreFullException` guard is gone structurally. The regression test
inverts the previous test that documented the busy-spin behavior.

### Pool disposal robustness

A faulting adapter `DisposeAsync` no longer aborts disposal of the
remaining pooled connections.

## Tooling

`CA1031` (do not catch general exception types) is enforced as a build
error via `src/.editorconfig` + `<WarningsAsErrors>CA1031</WarningsAsErrors>`.
Every intentional catch-all/swallow site carries
`#pragma warning disable CA1031` with its justification on the pragma line,
so unmarked swallows can no longer be introduced silently.

## Compatibility Notes

- Public API addition: `SmtpFailureKind.Unclassified` (baseline moved to
  `PublicAPI.Shipped.txt`).
- Dashboards tracking `pooledmailkit.send.classification.count` may see the
  new `Unclassified` failure-kind tag; `SendFailedCount` is not recorded
  for unclassified failures (the raw exception is the signal).
- Startup behavior change: invalid `SecureSocketOptions`, missing
  `Password` with `UserName`, and negative retry settings now stop the
  process at startup instead of cycling create-failures at runtime.

## Known Limits

- The carried-over limits from 0.1.1 still apply (envelope rejections are
  non-retryable regardless of status code; keep-alive failures do not
  contribute to host-level suppression).
- `SmtpStageAwareException` / `ISmtpStageAwareException` remain `internal`
  and are never thrown by production code; whether to publish the
  stage-aware seam for external adapters is an open design decision.
